# Bug Assessment: Focused-vault operations depend on a warm vault-name cache

- **Slug**: bi-0121
- **Created**: 2026-11-04
- **Source**: pasted text (backlog item BI-0121, the cohort follow-up to BI-0117; no URL supplied, so the URL trust policy did not apply)
- **Verdict**: valid
- **Severity**: medium

## Report (verbatim or summarized)

Condensed from the pasted BI-0121 text:

> Latent regression risk across the active-mode surfaces of five typed tools (0.9.0 source): a hard `Vault not found.` failure on `prepend` (active mode) and on `find_and_replace` with a `file` locator and no `vault`, and a wrong `vault` value — the vault's absolute folder path instead of its display name — in the responses of `append_note`, `patch_heading` and `patch_block`. The bug fires only on a cold registry cache — every caller-session that has issued ANY prior specific-mode call against a registered vault primes the cache and masks the bug.

The 2026-11-03 re-validation (read-only, against 0.9.0) says the mechanism is unchanged: the registry's reverse lookup `resolveVaultDisplayName` is synchronous, returns `null` on a cold cache, and nothing fills the cache at start-up; the `?? base` fallback now lives once in `src/tools/_active-file.ts`. It ticks off `set_property` (takes the vault name from Obsidian's own answer), `write_note` (no `vault` in its response) and, since BI-0060 shipped in 0.9.0, `read`, `outline`, `rename` and `move` (their active mode sends no `vault=` and never consults the lookup). It records that BI-0117's two passing TC-00446 runs most likely had a primed cache, so BI-0117's ship does not protect `prepend`, and that no cold-cache TC exists for any cohort tool. Fix options named: make the reverse lookup fill the cache on demand (BI-0117 fix path 1), or stop sending a looked-up name to Obsidian (BI-0060's shape) and fail loud when a response name cannot be resolved (fix path 2). A side finding (not re-checked) says `obsidian.exe` crashes with exit 4294967295 on a `vault=<absolute path>` input, while `Obsidian.com` answers `Vault not found.` with exit 0.

The pasted text closes with a `/speckit-specify` prompt ("Stabilise focused-vault operations") whose acceptance criteria this assessment treats as the expected behaviour: the first call in a fresh session behaves the same as a later one; every edit to the focused note reports the vault by its display name; `find_and_replace` with a `file` and no `vault` works as a first call; the no-active-note failure and the already-immune tools are unchanged; a focused vault that genuinely matches no listed vault fails with a clear message naming that state, never a "vault not found" caused by passing on the folder location; and each in-scope operation's fresh-session scenario is checked for every release. Out of scope: adding focused-note support elsewhere, changing any operation's inputs, the already-immune tools, and how Obsidian answers an unknown vault.

## Symptom

On a fresh server, before any call has named a vault, the vault registry's reverse lookup (folder path to display name) has an empty cache and returns `null`; the shared helper then uses the vault's absolute folder path as its "display name". Active-mode `prepend`, and `find_and_replace` with a `file` locator and no `vault`, send that path to Obsidian as `vault=` and fail with `Vault not found.`; active-mode `append_note`, `patch_heading` and `patch_block` succeed but report the folder path in the response's `vault` field. Expected: the first call behaves like any later one, acting on the focused vault and reporting its display name, and a vault that truly cannot be identified fails with a clear, specific error.

## Reproduction

1. Start a fresh `obsidian-cli-mcp` server process (cold registry cache) and focus a note in `TestVault-Obsidian-CLI-MCP` (see `.memory/test-execution-instructions.md`; restarting the server is an owner action).
2. As the very first call of the process, call `prepend({ target_mode: "active", content: "x" })`. Expected from source: `CLI_REPORTED_ERROR` carrying Obsidian's `Vault not found.` answer, because the argv carries `vault=<absolute folder path>`.
3. In a new fresh process, as the first call, call `find_and_replace({ file: "<note name>", pattern: "a", replacement: "b", mode: "literal", commit: false, ... })` with no `vault`. Expected from source: the `obsidian file vault=<absolute folder path> file=<name>` lookup fails the same way.
4. In new fresh processes, as the first call each, call active-mode `append_note`, `patch_heading` and `patch_block` on the focused note. Expected from source: success, with `vault` equal to the absolute folder path instead of `TestVault-Obsidian-CLI-MCP`.
5. Repeat steps 2–4 after a first call that names the vault (for example `files` or `vaults`). Expected: all succeed and report the display name (the cache is primed).

Steps 2–4 are inferred from the source and from the unit tests that pin the fallback (listed below); they have not been observed live on 0.9.0. BI-0117's 2026-05-26 bisect observed step 2 live on an earlier version. Resolved (Relay): there is no live pre-fix reproduction. The owner runs one fresh server process per cohort tool in `/speckit-bug-test` on the fixed build (see Open Questions, live confirmation).

## Suspected Code Paths

- `src/vault-registry/registry.ts:107-113` `resolveVaultDisplayName()` — returns `null` when `cache === null` and never calls `probe()`, unlike `resolveVaultPath()` (lines 88–103), which probes on a miss (068 FR-037). This is the root cause. The interface doc comment (lines 29–40) documents the cold-cache `null` and the "caller falls back to the basePath literal" contract.
- `src/tools/_active-file.ts:207-209` `resolveVaultDisplayName(vaultRegistry, base)` — the shared helper's `?? base` turns the `null` into the absolute folder path.
- `src/tools/_active-file.ts:223-233` `resolveActiveLocatorWithVault()` — puts that value in `vaultDisplayName` for every active-mode caller of `resolveFsTarget` (`src/tools/_file-target.ts:75-84`): `append_note`, `prepend`, `patch_block`, `patch_heading`.
- `src/tools/prepend/handler.ts:180-192` — sends `vault: input.vault ?? vaultDisplayName` to the CLI `prepend` command, so in active mode the folder path becomes `vault=`; the same value also feeds `noteNotFound`, `classifyUpstreamFailure`, the `FS_WRITE_FAILED` details and the response (lines 156, 194, 212, 229).
- `src/tools/find_and_replace/handler.ts:487-491` `resolveSingleNoteScope()` — for a `file` with no `vault`, `resolveVaultDisplayName(deps.vaultRegistry, rawRoot)` feeds `findFileByTsv`, which sends `vault=<value>` to the CLI `file` command. The raw (pre-realpath) root is intentional (`refactor-decisions.md` item 17) and stays.
- `src/tools/append_note/handler.ts`, `src/tools/patch_block/handler.ts`, `src/tools/patch_heading/handler.ts` — write through the filesystem in active mode and only echo `vaultDisplayName` in the response (and error details), so the defect is the wrong value, not a failure. Their post-write metadata refresh already passes `input.vault`, not the display name (`refactor-decisions.md` item 24).
- `src/server.ts:100-108` — builds the registry with an `invokeProbe` that runs `obsidian vaults verbose`; no start-up priming. No change is proposed here.

Checked and immune, as the report says: `set_property` (its eval returns `app.vault.getName()`), `write_note` (consumes `resolveActiveFocusedFile` directly, no `vault` in its output), `read` / `outline` / `rename` / `move` (BI-0060 / commit `5cf24a1`: active mode sends `path=` with no `vault=` and carries no registry), `query_base` and `find_and_replace`'s folder and vault-wide scopes (they use the base path only as a filesystem root, never as a name). `find_and_replace`'s `active_note` fork uses `resolveActiveFocusedFile` and no display name.

Tests that pin today's behaviour (they will change with the fix): `src/vault-registry/registry.test.ts:310` ("returns null when the cache has not been primed"), `src/tools/_active-file.test.ts:255` and `:261` (helper falls back to the base path, with and without the method), `src/tools/append_note/handler.test.ts:952`, `src/tools/prepend/handler.test.ts:792`, `src/tools/patch_block/handler.test.ts:799` and `src/tools/patch_heading/handler.test.ts:747` (each "envelope falls back to the base path when the reverse lookup returns null"). Found after the Q3 ruling: `src/tools/_active-file.test.ts:225` (`resolveActiveLocatorWithVault` falls back to the base path) also pins the fallback, and `registry.test.ts:172`, `:189` and `_active-file.test.ts:245` call the lookup synchronously, so they break once it is async (see Open Questions).

## Root Cause Hypothesis

The reverse lookup reads only the in-memory cache and never fills it, while the only code that fills the cache is a forward lookup (`resolveVaultPath`) or `list()`. A session whose first call is active-mode therefore always misses, and the shared helper silently substitutes the folder path for the name (a Principle IV silent fallback). Where that value is only echoed, the response is wrong; where it is sent to Obsidian as `vault=`, Obsidian rejects it. A primed cache hides the defect, which explains why BI-0117's TC-00446 runs passed without a code change. Confidence: **high** for the mechanism (read directly from the source; the cold-cache `null` and the fallback are both pinned by unit tests). **Medium** for the exact live failure shape on 0.9.0 (`CLI_REPORTED_ERROR` with `Vault not found.` via `Obsidian.com`), which was last observed live in BI-0117's bisect.

- **Blast radius**: the helper `resolveVaultDisplayName` has its callers in `_active-file.ts` (`resolveActiveLocatorWithVault`) and `find_and_replace/handler.ts`; `resolveActiveLocatorWithVault` is called only from `_file-target.ts`; `resolveFsTarget` is called by `append_note`, `prepend`, `patch_block` and `patch_heading`. It adds one `UpstreamError` construction site in `_active-file.ts` using an existing top-level code (no new code; Principle IV streak preserved). `server.ts` is untouched: the registry already receives its `invokeProbe` there, and the reverse lookup reuses the same single-flight `probe()`.

## Proposed Remediation

**Preferred** (BI-0117 fix path 1 plus a fail-loud helper):

1. **Registry: make the reverse lookup fill the cache on a miss.** In `createVaultRegistry` (`src/vault-registry/registry.ts`), change `resolveVaultDisplayName` to an async method that checks the cache and, on a cold cache or a miss, calls the existing single-flight `probe()` once, then matches again, returning the name or `null`. This mirrors `resolveVaultPath`'s probe-on-miss (068 FR-037), so a vault added after start-up also resolves without a restart. Widen the interface type to `(basePath: string) => string | null | Promise<string | null>` and keep it optional, so the existing synchronous test stubs still compile (the "keep it optional" ruling in `refactor-decisions.md` Declined cleanups stands). Update the interface doc comment, which documents the old fallback contract.
2. **Helper: fail loud instead of falling back.** Make `resolveVaultDisplayName(vaultRegistry, base)` in `src/tools/_active-file.ts` async; it awaits the registry and, when the result is `null` (or the method is absent), throws a classified `UpstreamError` that names the state: the focused vault's folder matches no vault Obsidian lists. It never returns the folder path. Per the Q2 ruling (Open Questions, failure classification) it is `CLI_REPORTED_ERROR` with `details: { code: "VAULT_NOT_FOUND", reason: "focused-unregistered" }`, no disk path in the message or `details`, and a message that names the state and the remedy (call in specific mode with `vault`, or re-open the vault in Obsidian). `resolveActiveLocatorWithVault` awaits it. This is the owner's recorded fallback from the BI-0060 ruling ("fail loudly on a null reverse lookup and never forward the absolute path as `vault=`", `refactor-decisions.md`, file-type section (b)).
3. **find_and_replace**: `await` the helper at `handler.ts:487`. Keep the raw-root argument (item 17).
4. **No other handler change.** `prepend` keeps forwarding `vaultDisplayName` as `vault=`: after the fix it is always a registered display name. `append_note`, `patch_block` and `patch_heading` need no code change; their response now carries the display name.
5. **Docs**: correct `docs/tools/patch_heading.md:202` (documents the folder-path fallback) and `docs/tools/patch_block.md:163`, and add the new failure to the error tables of the five cohort tools' docs pages. No tool description or schema text mentions the fallback, so the FR-018 fingerprint baseline should not move (to be confirmed by the gate).

**Alternatives**:
- *Add BI-0060's shape on top* (fix path 3): active-mode `prepend` and the `find_and_replace` `file` lookup send no `vault=`, as `read` / `outline` / `rename` / `move` do. Not needed once the name is always registered, and it does not fix the response `vault` field on its own, so the fail-loud lookup is still required. It would add argv changes to two tools (and their pinned argv tests) for no further acceptance criterion. Rejected as redundant (see Open Questions, fix shape).
- *Fail loud only, no priming* (fix path 2 alone): every first active-mode call would fail with the new error, which contradicts the first-call acceptance criteria. Rejected.
- *Prime the cache at server start-up* in `server.ts`: adds a spawn to every start, touches the boot spine (`createServer`, a kernel node), and still misses a vault added later. Rejected.
- *Return the name from Obsidian's eval* (`app.vault.getName()`, as `set_property` does): changes the byte-stable `FOCUSED_FILE_TEMPLATE` that many tools and tests pin, and the eval name is not guaranteed to equal the `vaults verbose` display name. Rejected.

The current "returns null when the cache has not been primed" test changes to the probing expectation.

## Risks & Considerations

- **Existing tests must change.** Seven existing tests pin the bug, and four more break once the lookup is async (both sets are listed under Suspected Code Paths). Per `refactor-decisions.md` item 5, changing them needs explicit owner approval with the exact list (see Open Questions, test edits). If any other existing test fails, stop and raise it.
- **One extra spawn on a cold first call.** The first active-mode call of a process now runs `obsidian vaults verbose` once (single-flight, through the injected queue). `refactor-decisions.md` (write_note entry) records that `resolveActiveLocatorWithVault` "costs no extra spawn"; that note becomes stale and should be updated by the review. Handler tests count only the handler's `spawnFn`, and stub registries do not spawn, so spawn-count assertions are unaffected.
- **Exact path match.** The reverse lookup compares Obsidian's `app.vault.adapter.basePath` with the `vaults verbose` path by string equality. The primed-cache runs (TC-00446) show the two agree on Windows today; a host where they differ (case, separators, a trailing slash, a symlinked folder) would now fail loud instead of silently reporting the folder path. That is the intended direction, but a normalised comparison is not part of this fix.
- **Duplicate display names.** The name map keeps the last row for a duplicated name, so the reverse lookup cannot return a name for the earlier vault's path and will fail loud. Forwarding an ambiguous name would be no better; accepted residual.
- **Probe failure.** If `vaults verbose` itself fails (Obsidian down, CLI disabled per BI-0132), that error now surfaces from the cohort's active mode instead of the fallback. This is the correct cause, and the probe already carries the BI-0060 app-down recovery and the cold-start retry.
- **Side finding not addressed.** The `obsidian.exe` versus `Obsidian.com` difference only mattered because a folder path reached `vault=`; after the fix no folder path does, so it does not need a code change. It stays a Tool Notes item in the vault, not re-checked here.
- **ADR alignment.** Consistent with ADR-003 (target mode in typed tools; active mode stays uniform across the cohort), ADR-015 (`details.reason` sub-discriminator) and ADR-044 (which recorded the same fallback hazard for the file-path tools). No ADR conflict found.
- No security, migration or published-schema impact.

## Open Questions

- **Fix shape.** Resolved (Relay): option A. The reverse lookup probes once on a miss through the existing single-flight `probe()`, and the helper fails loud on a `null` after the probe. No new top-level code. If the probe itself fails, its error propagates, the cache stays unset, and the next call probes again (the Architecture's vault-registry caching rule: the cache is set only by a successful probe, which `probe()` already does by assigning `cache` only after a successful parse). Option B (BI-0060's no-`vault=` shape on top) and option C (fail loud without probing) were rejected. Rationale: BI-0117's Amendment ranks the registry auto-prime first and fail-loud second; A meets both the first-call criteria and the "genuinely unidentifiable vault" criterion. The Q1 answer's VALIDATION_ERROR rider was replaced by the Q2 ruling.
- **Failure classification.** Resolved (Relay): `CLI_REPORTED_ERROR` with `details: { code: "VAULT_NOT_FOUND", reason: "focused-unregistered" }`, a new ADR-015 `reason` value on the existing `VAULT_NOT_FOUND` pair. The message names the state and the remedy, for example "<tool>: the focused vault's folder matches no vault Obsidian lists; call in specific mode with `vault`, or re-open the vault in Obsidian." Neither the message nor `details` carries the absolute disk path (no `base` field), in line with BI-0185's `VAULT_NOT_FOUND`/`folder-missing` treatment of disk paths in errors as a leak. The new reason is listed in the error roster of each affected tool's `docs/tools` page. This supersedes the `details.reason`-only shape and the `base` field sketched under Proposed Remediation step 2. Rationale: ADR-015 keeps the category in `details.code` and the sub-state in `reason`; the acceptance criterion bans a "vault not found" failure caused by passing on the folder location, and a message naming the real state meets it.
- **Test edits.** Resolved (Relay): option A, exactly seven tests, changing only each test's expected result (the lookup probes and returns the name, or the call fails with `CLI_REPORTED_ERROR`/`VAULT_NOT_FOUND`/`focused-unregistered` and nothing is written): `registry.test.ts:310`, `_active-file.test.ts:255` and `:261`, `append_note/handler.test.ts:952`, `prepend/handler.test.ts:792`, `patch_block/handler.test.ts:799`, `patch_heading/handler.test.ts:747`. If any other existing test fails, stop and raise it; do not edit it. Ruling recorded on BI-0121.
- **Live confirmation.** Resolved (Relay): option A, a live check after the fix only, in `/speckit-bug-test` on the fixed build. The owner restarts the server once per tool, and the first call each time is that tool against a note focused in TestVault-Obsidian-CLI-MCP: active-mode `prepend`, `append_note`, `patch_heading` and `patch_block`, and `find_and_replace` with `file` and no `vault`. Each must succeed and report `vault: "TestVault-Obsidian-CLI-MCP"`. The live pre-fix reproduction is skipped; the in-process cold-cache unit tests (the real `createVaultRegistry` with a stub probe) cover the cold path. The five post-fix checks serve as the BI's per-tool regression-lock TCs (scope item 3). Ruling recorded on BI-0121.
- **Four more existing tests.** Resolved (Relay): option A. The owner approved four more edits, which brings the approved existing-test edits to 11 in total. The original test inventory missed these four, and making the registry method and the helper async (Q1 option A) breaks them. In `registry.test.ts:172` ("returns the registered display name for a known basePath"), `registry.test.ts:189` ("returns null for an unknown basePath") and `_active-file.test.ts:245` ("returns the registry display name when one resolves"), the only change is adding `await`; the expected values stay the same. In `_active-file.test.ts:225` (`resolveActiveLocatorWithVault` "falls back to the base path when the registry has no display name"), the only change is the expected result: `CLI_REPORTED_ERROR` with `details: { code: "VAULT_NOT_FOUND", reason: "focused-unregistered" }`. If any other existing test fails, stop and raise it; do not edit it. Option B, a separate optional async refresh method that would keep the lookup synchronous, was rejected. Ruling recorded on BI-0121.
