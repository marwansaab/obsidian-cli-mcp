Expected behaviour, condensed from the report's "Report blocked destinations" feature text:

- **Same failure however the note is chosen.** A move to `Blocker.md/`, where `Blocker.md` is an existing note in the same folder, fails with the "a file is in the way" failure (`NOT_A_FOLDER`) naming `Blocker.md`, whether the source is named by note name (`file`), by `path` (as today) or is the active note. In active mode the blocking file is looked up in the focused vault. The advice is to rename or remove the blocking file or choose another destination, never to create the folder. Nothing changes on disk.
- **Description names the failure.** The `move` tool's short description names `NOT_A_FOLDER`; the help page still documents it.
- **Other failures unchanged.** A genuinely missing destination folder still reports `FOLDER_NOT_FOUND`; a file that already exists at the full destination path still reports that the destination file exists.
- **Out of scope.** Creating destination folders; renaming or removing the blocking file; other tools' descriptions and the overall description budget.

## Symptom

`move` with `to` in the folder form (trailing `/`) whose last folder segment is an existing file returns the raw `CLI_REPORTED_ERROR` `Error: Destination file already exists!`, with no `details.code`, when the source is named by `file` (TC-00865 step 4) or is the active note (TC-00900). The same call by `path` returns `NOT_A_FOLDER` naming the file. Expected: `NOT_A_FOLDER` for all three locators. Separately, `MOVE_DESCRIPTION` does not name `NOT_A_FOLDER` (TC-00867).

The CLI then expands the folder form itself.

## Root Cause Hypothesis

PR #139 put the blocked-destination lookup behind the CLI's ENOENT/ENOTDIR rename line, which is what the CLI prints when it is handed a full destination path through a file. The handler hands it that full path only for a `path` locator. For `file` and active calls it forwards the raw folder form, the CLI expands it itself, and for a folder segment that is an existing file it answers `Destination file already exists!` (spec 090 P5), a line `moveFailure` never sends to the lookup. The unit row for active mode (B7) stubbed the ENOENT line instead of the line the CLI sends, and no row covered the `file` locator, so the gap was not visible in tests. Confidence: **high**. The code path is certain, and both variants are observed live (TC-00865 step 4, TC-00900). The description gap is a plain omission, confirmed on the live `tools/list`.

## Proposed Remediation

**Preferred** (keeps every forwarded argument byte-stable):

1. **Send the folder-form "already exists" answer to the lookup.** In `moveFailure`, when the folder form was forwarded unexpanded (`file` or active locator, `to` ending in `/`, the same condition `executeMove` already computes for `forwardedTo`) and the CLI's error is `CLI_REPORTED_ERROR` with `details.message` equal to `Error: Destination file already exists!`, run the existing `findBlockingFile(destinationFolder(resolvedTo), target.vault, deps)` exactly as the ENOENT branch does. A blocker → `notAFolder(blocker)`. No blocker → the failure is today's: the CLI error with the vault root rewritten out (a genuine existing destination file, for example `to: "Archive/"` where `Archive/Note.md` exists). A failed lookup → `withheldFailure(…, "destination-folder", …)`, the first round's Q2 rule; cancellation passes through untouched. The trigger is restricted to the unexpanded folder form so that every other "already exists" failure, including M15's full-path `to` and every `path` call, stays one spawn with no lookup. The lookup vault rule is unchanged: `target.vault` in specific mode, `undefined` (the focused vault, no `vault=`) in active mode.
   The ENOENT/ENOTDIR branch is unchanged, so `path` calls (TC-00701, B1–B6) and genuine missing folders through any locator (M1–M7) behave exactly as today.
2. **Name the failure in the description.** Per the owner's 2026-11-05 ruling, `MOVE_DESCRIPTION` drops ` (change it with \`obsidian_exec\`)` and gains one sentence naming `NOT_A_FOLDER`, for example `A destination through an existing file fails with \`NOT_A_FOLDER\`.` placed before the file-type sentence, which gives 397 characters, within `DESCRIPTION_BUDGET` (400) with no audit exception. The fix must measure the final string and keep it at or under 400. The `index.ts` header's "not in the description" clause is corrected. `docs/tools/move.md` already documents `NOT_A_FOLDER` (line 157) and the `obsidian_exec` routing (lines 7 and 21), so it needs only the `file`/active wording below.
3. **Docs.** `docs/tools/move.md`'s `NOT_A_FOLDER` row (line 157) gains that the failure is the same for `path`, `file` and active calls. The `Destination file already exists!` row (line 155) is unchanged in meaning; it may add that a folder-form `to` through a file is reported as `NOT_A_FOLDER` instead. `src/tools/move/handler.ts`'s attribution header summary is updated to name the new trigger.

**Alternatives**:
- *Expand the folder form for every locator* (always forward `resolvedTo`). The CLI would then get the full path through the file, answer the ENOENT line, and the existing branch would classify it, with less handler code. Rejected for `file` calls: it changes `file`-mode `to=` arguments, which spec 070 `contracts/tool-support.md` invariant 4 fixes as byte-stable, and it would change rows M5 and B-series argv assertions and the `file`-mode tests the invariant protects. Expanding only for active calls is allowed by the invariant (it covers `path` and `file`), but it fixes one of the two variants and leaves two mechanisms for one failure; the preferred trigger covers both with one rule.
- *Send every `Destination file already exists!` to the lookup, whatever the `to` shape.* Simpler condition, but it adds an eval and a new failure mode (the withheld failure) to every genuine destination collision by `path` or full-path `to`, which the report's "other failures unchanged" story protects. Rejected.

## Risks & Considerations

- **Exact-string trigger.** The trigger matches the CLI's `Error: Destination file already exists!` text. A future CLI wording change would silently restore today's raw error (not a wrong classification). The row that stubs the captured line is the guard; the T0 capture makes it a recorded line, not an assumption.
- **Extra eval on a folder-form collision.** A `file` or active move with a folder-form `to` onto a genuinely existing destination file now costs one eval, and a failing eval turns its raw message into the withheld failure. That is the first round's Q2 rule applied to a new branch; the plain collision message is kept whenever the lookup succeeds.
- **Description changes.** `MOVE_DESCRIPTION` is published surface; its fingerprint moves deliberately. Removing the `obsidian_exec` route from the description is the owner's 2026-11-05 ruling; the help page keeps it (`docs/tools/move.md` lines 7 and 21). The spec 070 assertion that names that route moves to the help page for `move` (Q1, resolved).
- **Total description budget.** The description grows by 33 characters net. `TOTAL_DESCRIPTION_BUDGET` (12,000) is checked by `_description-quality.test.ts`; the fix runs it.
- **Case-insensitive file systems and absolute paths.** Unchanged from round one: the lookup is the disk-based `BLOCKER_TEMPLATE`, and the `NOT_A_FOLDER` failure is built from vault-relative strings only.
- **Spec traceability.** Completes spec 090's edge case for every locator. Acceptance evidence: TC-00865 step 4, TC-00867 and TC-00900 on the next local build.
