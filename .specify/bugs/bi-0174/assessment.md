# Bug Assessment: help pages and tool descriptions disagree with live behaviour

- **Slug**: bi-0174
- **Created**: 2026-11-04
- **Source**: pasted text (backlog item BI-0174, filed 2026-11-02 from the 0.9.0-local test run; follow-up to BI-0166, same class as BI-0105 and BI-0122)
- **Verdict**: valid. Most items are confirmed by reading the current code on `main` (29def6a). Some sub-items have already been fixed by BIs merged since the report was filed (BI-0175, BI-0176, BI-0180, BI-0182, BI-0132), and the audit found more instances of the same defects than the report lists. A few sub-items rest on live behaviour that the code alone cannot show; the fix confirms those live before changing them.
- **Severity**: medium

## Report (verbatim or summarized)

Condensed from the pasted BI-0174 text:

> The `help` tool and the tool descriptions are the agent's only map of the server. After 0.9.0's fixes they still disagree with live behaviour. Harms: (a) false advertisement on the published surface; (b) error-branching code written against the docs never fires; (c) recovery hints send agents to tools, commands or actions that do not work; (d) inconsistent page structure defeats agents and tests that navigate help by section.
>
> 1. Help page heading structure (TC-00586): only 11 of 35 pages have H2 headings beginning `Input`, `Output`, `Errors` and `Examples`.
> 2. Server instructions: "Unsupported file types fail with UNSUPPORTED_FILE_TYPE" is not true cohort-wide (`find_and_replace` → `INVALID_NOTE`; `links`, `backlinks`, `smart_connections_similar` → `NOT_MARKDOWN`; Base tools → `INVALID_BASE_PATH`).
> 3. Vault-unavailable example: seven tools give "CLI integration disabled" as the cause with a `Command "…" not found` output; TC-00495 observed `Command line interface is not enabled.`.
> 4. Unknown-vault claims: `prepend`, `append_note`, `patch_block`, `patch_heading` claim `VAULT_NOT_FOUND` (live: `VALIDATION_ERROR` with `requestedVault` / `knownVaults`); `smart_connections_similar`, `smart_connections_query`, `tag` (and `search`, unverified) claim `VAULT_NOT_FOUND` / `unknown` (live: plain `CLI_REPORTED_ERROR` "Vault not found."); `find_and_replace`'s hint names the CLI command `obsidian vaults` instead of the `vaults` tool.
> 5. `context_search`: missing-folder error said to propagate "verbatim — no wrapping" (TC-00597); `...` cut marker; omits leading-whitespace preservation and `MATCH_LINE_UNAVAILABLE`; lacks the Cowork `-32602` caveat; ASCII-only case-fold claim (unverified); "literal substring" wording to re-check after BI-0175.
> 6. `outline` Example 4 shows a top-level `Error: File "Missing.md" not found.` message; live is wrapped (TC-00600).
> 7. `patch_heading` documents `EMPTY_CONTENT` in `details`; live returns the generic schema-validation envelope (TC-00600). Either the doc or the error mapping changes.
> 8. `find_and_replace`: quoted messages lack the `find_and_replace: ` prefix (TC-00601); description is 4,825 characters, past Claude Code's 4,096 cut; `deprecated_parameters` scope; `folder` vs `INVALID_SUBFOLDER` (follows BI-0182).
> 9. `write_note`: description omits that `bytes_written` is a size change; `file` resolution wording (follows BI-0176).
> 10. Bases family: `create_base` described as creating a `.base` file; `bases` index says `vault` is ignored (unverified); `query_base` sample type of `priority` (unverified); `create_base` Output (follows BI-0180); `views_base` no-active-file advice names `target_mode` / `file`, which `views_base` lacks; validation-error and `PATH_ESCAPES_VAULT` shapes to be stated as returned; `views_base` and `query_base` document different `INVALID_BASE_PATH` shapes (unverified).
> 11. `links` `target` called "byte-faithful" while live decodes `%20` (TC-00670); `NOT_MARKDOWN` hints send attachments to `read`, which rejects them (TC-00682); `smart_connections_similar` Overview shows `find_connections({limit})`.
> 12. `delete` help says it deletes a single note; it deletes any file type (TC-00692).
> 13. `read`'s `UNSUPPORTED_FILE_TYPE` message ends "Nothing was changed.", which is odd for a read-only tool.
>
> **Owner decision (2026-11-02):** TC-00586's strict heading rule stays; every page is renamed to use `Input`, `Output`, `Errors` and `Examples` (suffixes such as `Output (success)` allowed).

Acceptance criteria (summarised from the report's `/speckit-specify` section): every help page has sections beginning "Input", "Output", "Errors", "Examples"; every example error matches the returned code, message and detail fields; quoted messages and codes match the server's wording, including any tool-name prefix; recovery hints name a tool that accepts the file, a callable tool for unknown vaults, and only inputs the tool accepts; every description fits within 4,096 characters; the server's general guidance on unsupported files and unknown vaults is true, or names the per-tool exception.

Out of scope (per the report): behaviour changes other than errors that must change to agree with their docs; the behaviour defects tracked separately (partial-word search, overwrite by name, move destination blocked by a file, missing named note in find-and-replace, stale Base parser messages, Base created-item path, tag hash prefixes, retired input names in errors); relaxing TC-00586; style or length rewrites.

## Symptom

The published guidance (help pages in `docs/tools/*.md`, the tool descriptions and input-schema descriptions in `src/tools/*/index.ts` / `schema.ts`, and the server instructions in `src/instructions/instructions.ts`) describes error codes, messages, detail fields, recovery advice and section structure that differ from what the server returns. Expected: every page uses the standard section names, and every quoted error, example and hint matches today's behaviour.

## Reproduction

Read-only probes run during this assessment, with no vault and no CLI involved:

1. **Headings.** List the `## ` headings of every `docs/tools/*.md` page except `index.md`, and check for headings beginning `Input`, `Output`, `Errors`, `Examples`. The result matches the report exactly: the same 24 pages are short, with the same missing sets (21 lack `Errors` and `Examples`; `get_active_file` lacks `Input` and `Errors`; `open_file` lacks `Output` and `Errors`; `write_note` lacks `Errors`).
2. **Description lengths.** List the tools through an in-memory client (`createServer().buildMcpServer()` plus `connectInMemoryClient`) and measure each `description`. `find_and_replace` is **4,867** characters (it has grown since the report's 4,825, through BI-0182's wording). Every other tool is under 4,096; the next longest is `pattern_search` at 3,484.
3. **Unknown-vault shapes.** Reading the code shows three shapes, depending on how a tool resolves its vault:
   - Registry-resolved tools without a remap (`append_note`, `prepend`, `patch_block`, `patch_heading`, `write_note`, and `read`, `outline`, `move`, `rename` in specific mode): `VALIDATION_ERROR`, message `Vault "<name>" is not registered with Obsidian.`, `details: { requestedVault, knownVaults }` (`src/vault-registry/registry.ts:114-120`).
   - Tools that remap the registry error (`bases`, `create_base`, `find_and_replace`, `get_active_file`, `open_file`, `query_base`, `views_base`): `CLI_REPORTED_ERROR`, `details: { code: "VAULT_NOT_FOUND", reason: "unknown", vault }`, message `<tool>: vault "<name>" is not registered` (`src/tools/_active-file.ts:316-326`).
   - CLI-only tools (among them `search`, `context_search`, `pattern_search`, `tag`, `links`, `backlinks`, `paths`, `smart_connections_query`, `smart_connections_similar`): `CLI_REPORTED_ERROR` with message `Vault not found.` and `details: { command, stdout, stderr, exitCode: 0, message }`, with no `details.code` and no `reason` (`src/cli-adapter/cli-adapter.ts:151-159`).
4. **Wrapped errors.** The dispatch layer's `Error:`-prefix rule (`src/cli-adapter/_dispatch.ts:677-687`) builds `UpstreamError` without a `message`, so the top-level message is the default `CLI bridge upstream error: CLI_REPORTED_ERROR` (`src/errors.ts:16`). The original line goes in `details.message`. The same default applies to `PATH_ESCAPES_VAULT` from `assertCanonicalPath` (`src/tools/_active-file.ts:412-416`).
5. **Schema-layer sub-codes.** `registerTool`'s generic validation envelope (`src/tools/_register.ts:187-192`, `validationIssues` at `:65-69`) keeps only `path`, `message` and `code` for each issue. The `params` that schema refinements attach (`{ code, reason, … }`) never reach the caller unless the tool supplies a `mapValidationError` hook. Only `create_base`, `find_and_replace` and `prepend` do, and `prepend`'s hook lifts only the size-limit issues.

Items marked *unverified* in the report, and the live-only facts listed under each item below, are confirmed against the authorised test vault during `/speckit-bug-fix`, following `.memory/test-execution-instructions.md`.

## Root Cause Hypothesis

Confidence high. The defects share one cause: behaviour changed in later specs and BIs (spec 072's vault-unavailable rework, spec 091's unknown-vault answer, BI-0132's disabled-CLI error, the registry-based specific-mode resolution of the write cohort, the `Error:`-prefix rule's default message), and the hand-written prose describing it was not updated in step. Nothing ties a help page, a description or a quoted message to the code that produces the error. The help docs-sync test (`src/tools/help/docs-sync.test.ts`) checks only that pages and index entries match the offered tools. Nothing checks section names (the owner's TC-00586 rule), description length, or quoted wording. BI-0166 FR-009 was a docs-only promise with no test, which is why it "did not land". The schema-layer sub-code gap (item 7) is the one place where the code, not the prose, may be at fault. The refinements attach `params.code` / `params.reason` as ADR-015 sub-discriminators intend, but the generic envelope in `registerTool` drops `params`, so the documented `details.code` / `details.reason` only reach callers on the three tools that supply a hook.

## Proposed Remediation

**Preferred** (item 7 follows the owner's Q1 ruling, option C; see Open Questions):

1. **Headings (item 1).** Rename the H2 headings on the 24 pages so each page has headings beginning `Input`, `Output`, `Errors`, `Examples`. Keep the old wording as a suffix, for example `## Errors — Error roster`, `## Examples — Worked examples` or `## Output (success)`. The suffix keeps the strings existing tests assert, so no test needs editing (see Tests to add or update). `get_active_file` gets an `## Input` section (its "Targeting — two modes" content goes under it); `open_file` gets an `## Output` section stating what it returns. Leave every other heading as it is. Fix the two `#error-roster` anchors to the renamed headings' slugs. Add one cohort test to `src/tools/help/docs-sync.test.ts`: every page in `listToolPages(DOCS_DIR)` has an H2 beginning with each of the four words. This is TC-00586's rule as a regression lock.
2. **Server instructions (item 2).** Make the rule name its exception. To keep `instructions.test.ts:95` unedited (owner rule: new tests only), keep the pinned sentence verbatim and append the exception, for example: "- Unsupported file types fail with UNSUPPORTED_FILE_TYPE; renames and moves keep the type. A tool whose description names another code for this uses that code." The line must name no tool in backticks: `offered()` drops any line whose backticked tools are not all offered (`instructions.ts:40-42`), so listing the exceptions by tool would make the rule vanish when one of them is disabled. A new test pins the added sentence.
3. **Disabled-CLI row (item 3 residue).** Add the `CLI_REPORTED_ERROR` / `details.reason: "cli-disabled"` row, worded as on `vaults.md:57`, to the seven pages the report names, next to their vault-unavailable row. Keep the vault-unavailable rows; confirm live that a vault that cannot be brought up still answers `Error: Command "…" not found.`.
4. **Unknown vault (item 4).** For each tool, state the shape the tool actually returns (Reproduction 3). On the 4a pages and descriptions, the shape is `VALIDATION_ERROR` with `requestedVault` / `knownVaults`. On the 4b pages, descriptions and `search/schema.ts:59`, it is `CLI_REPORTED_ERROR` with message and `details.message` `Vault not found.` and no code or reason; drop `VAULT_NOT_FOUND(unknown)` from the two Smart Connections precedence chains, or replace it with the real shape. Every unknown-vault hint, including the three `obsidian vaults` hints, points to the `vaults` tool. Do not change the shapes themselves: spec 091 keeps "how the dedicated tools report unknown vaults" out of scope.
5. **`context_search` (item 5).** Correct `:88`, `:181` and `index.ts:31` to say the missing-folder error is wrapped, with the generic top-level message, and that callers branch on `details.command` / `details.message`. Add one sentence each to the description on leading-whitespace preservation and `MATCH_LINE_UNAVAILABLE`. Add the `-32602` caveat to the help roster. Replace the ASCII-only fold claim (both tools: descriptions, `case_sensitive` field descriptions, help pages) with what spec 087 F7 observed: the default fold covers at least Latin-1 letters. Confirm live once more before rewording.
6. **`outline` Example 4 (item 6).** Show the returned envelope: top-level `CLI bridge upstream error: CLI_REPORTED_ERROR`, with the `Error: …` line in `details.message`.
7. **Schema-layer sub-codes (item 7 and its new instances).** Per the owner's Q1 ruling (option C), lift only where the docs already promise the lifted shape. A shared `mapValidationError` helper copies a refinement's `params` (`code`, `reason`, plus extra keys such as `field` or `value_length`) into `details`, keeps the issue's own message, and keeps `details.issues` unchanged alongside, following `create_base`'s `mapZodIssuesToToolError` (BI-0166 FR-008, ADR-015) as the template. `patch_heading` (`EMPTY_CONTENT`, `INVALID_HEADING_PATH`), `patch_block` (`INVALID_BLOCK_ID`) and `query_base` (`INVALID_BASE_PATH`, `INVALID_VIEW_NAME`) use it. `append_note` gains a hook, and `prepend` extends its existing one, mapping the empty-content `too_small` on `content` to `details.code: "CONTENT_EMPTY"`. The pages and descriptions of these five tools are then re-read against the lifted shape and corrected only where they still differ (for example `patch_heading.md:152-153` names `details.reason` values the refinements must actually carry). **`views_base` keeps the generic envelope.** Its live error already matches `views_base.md:57,159-165`, so neither its code nor that part of its page changes. Item 10's "state each as returned" is met by `query_base.md` showing the lifted shape and `views_base.md` showing the generic one, each as returned.
8. **`find_and_replace` (item 8).** Add the `find_and_replace: ` prefix to every quoted message, after re-checking each against `handler.ts`. Cut the description to 4,096 characters or fewer by moving long detail (roster prose, examples) to the help page, which keeps it. Keep the decided success-only and `INVALID_SUBFOLDER` sentences. Add a cohort test asserting that every published description is at most 4,096 characters, so the next growth fails CI. `pattern_search` (3,484) and `open_file` (3,348) are the nearest to the cap.
9. **`write_note` (item 9a).** Add one clause to the description: on overwrite, `bytes_written` is the change in size and can be zero or negative.
10. **Bases family (item 10).** Fix the `query_base` sibling wording and routing row so `create_base` adds an item to an existing Base. Correct `index.md:7` for `bases`. Make the two `priority` samples agree with a live run. Re-read the `create_base` Output sample. Give `views_base` a tool-specific `ERR_NO_ACTIVE_FILE` message: catch the dispatch error in `listFocusedViews` and rethrow the same code and details with advice that names only its inputs (open a Base in Obsidian, or pass `base_path`). Give `obsidian_exec` the same treatment, with advice to open a file or name one in the command's own parameters. Leave the dispatch message unchanged for the tools that do have `target_mode`. ## Risks & Considerations

- **Published-surface change.** Descriptions, two input-schema field descriptions and the instructions change, so the FR-018 fingerprint moves for many tools in one regeneration. That is a deliberate gate, called out in the PR.
- **Behaviour changes are confined to errors.** The Q1 lift (five tools, not `views_base`), the `views_base` / `obsidian_exec` advice and the read-only message change only error `details` and messages, which the report allows ("except where an error must change so that it and its documentation agree"). - **Principle IV.** No new top-level error code. The lift adds `details.code` / `details.reason` values that already exist in the docs and the schemas; `views_base` / `obsidian_exec` rethrow the existing `ERR_NO_ACTIVE_FILE` code.

- **Q1 — Schema-layer sub-codes (item 7 and its new instances): change the docs, or lift the sub-code into `details`?**

  Context: `registerTool`'s generic envelope (`src/tools/_register.ts:187-192`, `validationIssues` at `:65-69`) keeps only each issue's `path`, `message` and `code`, and drops the `params` that refinements attach.
