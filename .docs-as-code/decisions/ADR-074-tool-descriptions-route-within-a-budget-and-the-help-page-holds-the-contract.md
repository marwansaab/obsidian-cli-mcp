# ADR-074 — Tool descriptions route within a character budget, the help page holds the contract, and only mechanical checks gate

- **Status:** Accepted
- **Date:** 2026-11-04
- **Source:** PR #143 (spec 092, `specs/092-audit-tool-descriptions/`:
  Clarifications Q1 to Q6 of 2026-11-04, contract §S and §H, owner rulings
  on BI-0027), commits `b931e95` (the rewrite and the audit) and `867d939`
  (the code-quality review's typed verdicts, findings F1 to F3)
- **Related:** ADR-040 (published parameter descriptions and server
  instructions), which put the parameter rules in the schema and the
  cross-cutting rules in the instructions but set no length for a
  description; ADR-005 (Token-Optimized Tool Definitions via Progressive
  Disclosure), superseded by ADR-040, whose "~40–80 tokens" figure BI-0027
  had carried; ADR-045 (closed vaults are recovered only by the dispatch
  retry), whose decision 2 this PR's owner amendment changed; ADR-054 (help
  pages are checked against the offered tools by a test), which checks the
  pages' names; ADR-044 (file-path tools check the resolved file and keep its
  type), whose supported-types sentence every description keeps.

## Context

Every tool's description is loaded into an agent's context on every
session. Before PR #143 the 35 descriptions came to 62,067 characters; four
were under 400 and the longest was about 4,050. They carried result shapes,
caps, error rosters and examples that the tool's `docs/tools/` page also
held, several quoted internal tracking numbers, and nine repeated one shared
closed-vault paragraph. The only length rule was PR #142's 4,096-character
cap, the length at which Claude Code cuts a description. Nothing said what
a description is for, and nothing checked that related tools agreed with
each other.

## Decision

1. **A description routes; it does not document.** It says what the tool
   does, when to choose it over its named siblings, and any statement an
   agent needs to avoid data loss (overwrite, delete, links rewritten,
   vault-wide default, blocked commands), followed by ADR-044's supported
   file-types sentence. Result shapes, caps, edge cases, error codes and
   examples live on the help page only (FR-001 to FR-003). Before a fact
   left a description it was found on, or added to, that tool's page
   (FR-004, contract §H).
2. **Budgets.** At most 400 characters per tool and 12,000 for all of them
   together, counting only the top-level `description` (Q1). Parameter
   descriptions are not budgeted, but are checked for internal identifiers.
   PR #143 brought the total to 9,847.
3. **One source for the index.** Each `docs/tools/index.md` entry is, word
   for word, the first sentence of the tool's description (Q2). `help` still
   serves the index page as written; a test enforces the match.
4. **The pointer to the contract is said twice.** The last instructions rule
   says `help` with a tool's name returns its full contract, and `help`'s own
   description says the same, for clients that do not show instructions
   (FR-008, FR-009). No tool description repeats a call-help sentence
   (ADR-040).
5. **Mechanical checks gate; judgement does not.** Budgets, internal
   identifiers in every published text, the help pointer and index agreement
   are standing tests (`src/tools/_description-quality.test.ts`). The
   judgement verdicts (purpose, safety caveat, detail moved, self-contained,
   family, shared fields) live in a hand-kept reviewer record keyed by each
   tool's description and schema fingerprints. When a description changes,
   its recorded verdicts show as `NEEDS REVIEW` in the audit report and
   fail nothing (Q4, Q5).
6. **Routing is checked by a reviewer.** For each routing line in the
   server instructions, a reviewer checks that the descriptions alone send
   the task to the routed tool and that no sibling claims it, and records
   the result in the family verdicts (Q6).

## Alternatives rejected

- **A hand-written index entry that only has to agree with the
  description** (Q2). There is no mechanical test for "agrees", so the two
  texts drift. Copying the whole description instead would break the
  one-line-per-tool index format that BI-0030 set.
- **A hand-written audit report checked by a test, or the test results
  alone** (Q4). A hand-written report goes stale with the first description
  edit, and test output cannot carry the judgement verdicts or gap notes
  the release audit needs. The report is generated by
  `npm run audit:descriptions` from the live tool list.
- **Failing the tests on a stale judgement verdict** (Q5). That would put a
  description-quality sub-task on every feature PR, which BI-0027 exists to
  avoid. Stale verdicts are collected and cleared at the release audit.
- **A model evaluation of tool choice** (Q6). BI-0027 asks for no new
  evaluation tooling, and the connector best practice treats "the
  description alone is enough" as a reviewer step.
- **Moving every input rule into its parameter description** (Q3, partly
  taken). Allowed, at most one sentence and only where the parameter does
  not already say it; PR #143 found no rule that needed it.
- **Keeping the shared closed-vault sentence** (ADR-045 decision 2). It cost
  about 300 characters on each of nine tools and is long-reference
  material. The owner amended ADR-045 on 2026-11-04 so the help pages carry
  it instead.

## Consequences

- An agent sees a short routing text per tool and has to call `help` for
  anything else. The help pages are now the only place most result shapes,
  caps and error codes are written down, so a page that is wrong is wrong
  everywhere.
- A new tool or a description edit must fit 400 characters and must keep
  the total under 12,000; `_description-quality.test.ts` fails otherwise.
  PR #142's 4,096-character test in `_surface.test.ts` still runs, as an
  implied, looser check; deleting it needs the owner's approval under the
  existing-test rule (PR #143 review finding F4).
- Every description edit moves its fingerprint in both
  `_register-baseline.json` and the reviewer record's view of it. The
  baseline fails the build; the record only flags the tool for review.
- The four input root descriptions (`properties`, `query_base`,
  `read_property`, `search`) are still long reference blocks. PR #143
  removed only their identifiers and history; they are not budgeted, and
  shortening them is a follow-up.
- Help pages are not scanned for internal identifiers; only the published
  texts and the index are (spec 092 Out of Scope).
- No kernel node, handler, schema shape or error code changed (FR-022).
