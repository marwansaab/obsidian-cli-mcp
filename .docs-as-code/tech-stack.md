# Tech stack

What the server is built from, why each piece is here, and what having it
forces or rules out. `package.json` lists what is installed; this page records
what that costs. Where the [constitution](../.specify/memory/constitution.md)
(*Technical Standards & Stack Constraints*) mandates a choice, the rule is
there and only its effect is here. The stack was refreshed by BI-067
(PRs #74–#80), where the version holds below come from, and the MCP SDK moved
to v2 in PR #89 (spec 068, ADR-039).

## Language and runtime

| What | Why it is here | What it constrains |
| --- | --- | --- |
| Node.js, published floor `>= 22.11` | Runs the server; `engines.node` is what end users need. | Raising the published floor needs a constitution amendment citing the API that forces it. Newer built-ins (`fetch`, `AbortController`, `node:test`-era APIs) may be used; polyfills may not. |
| Node.js `>= 22.13` for development | ESLint 10 declares `^20.19 \|\| ^22.13 \|\| >=24`. | A dev-only floor, kept apart from the published one ([CONTRIBUTING.md](../CONTRIBUTING.md)). On an older 22.x, `npm run lint` fails while the server still runs. |
| TypeScript `~6.0.3` (tilde hold) | Strict typing; `tsc --noEmit` is the authoritative typecheck. | Held below 6.1 because typescript-eslint's peer range stops at `<6.1.0` (PR #76, PR #80). Raising it waits on typescript-eslint. |
| ES modules, `NodeNext` resolution, `ES2024` target | `"type": "module"`; imports end in `.js` even from `.ts` sources. | Lint's import resolver cannot follow the `.js`-on-`.ts` convention, so `import-x/no-unresolved` is off and the compiler does that job. `verbatimModuleSyntax` and `isolatedModules` require explicit `import type`. |
| `noUncheckedIndexedAccess`, `noUnusedLocals`/`Parameters`, `noImplicitReturns` | Stricter than `strict` alone. | Every indexed read is `T \| undefined`; code uses `!` only where a preceding check makes it safe (for example the first element of `split`). |

## MCP transport

| What | Why it is here | What it constrains |
| --- | --- | --- |
| `@modelcontextprotocol/server` `^2.4` (runtime) | The only MCP transport: `McpServer.registerTool` for every tool, and `serveStdio` serving both protocol eras on one stdio connection (PR #89, ADR-039). | Since PR #90 the tool's `title` and four behaviour-hint `annotations`, and the server `instructions`, reach clients through `registerTool` and the `McpServer` options rather than project code. `McpServer` validates input and formats errors itself, so tools reach it through the pass-through `toSdkInputSchema` adapter that keeps the project's zod parse and error envelope ([architecture](architecture.md#registration--the-one-path-from-a-schema-to-a-published-tool)). It checks `structuredContent` against `outputSchema` the same way, and reports a failure as free text, so since PR #91 typed tools hand it `toSdkOutputSchema`, whose validator also accepts everything, and `registerTool` runs the output check itself (ADR-042). Its 2025-era codec wraps an output schema without an object root, so `registerTool` refuses one at boot. The adapter tracks the SDK's Standard Schema contract, and the spike tests in `_register.test.ts` fail first if a minor release calls it differently. `serveStdio` builds a server more than once per connection, so shared state lives in `createServer`, not the factory. Unknown tool names are the SDK's JSON-RPC `-32602`. Since PR #92 the server also relies on three per-request SDK features: `ctx.mcpReq.signal` for cancellation, `ctx.mcpReq.notify` for `notifications/progress`, and the `input_required` result for confirmation, which the SDK fulfils natively on the 2026 era and through its legacy shim as `elicitation/create` on the 2025 era (ADR-043). The server still declares no Roots, Sampling or Logging capability. Needs zod ≥ 4.2 and Node ≥ 20, both already met. It replaced `@modelcontextprotocol/sdk` 1.x, whose low-level `Server` was kept behind `no-deprecated` disables until then (BI-067, PR #78); dropping v1's HTTP/Express dependencies shrank `package-lock.json` by about 2,800 lines. |
| `@modelcontextprotocol/client` `^2.4` (devDependency) | Test-side only: the in-process both-era protocol tests (`src/server.protocol.test.ts`), the fingerprint gate, `npm run probe:stdio` (PR #89) and `npm run check:non-ascii` (PR #144), which build their client with the shared `scripts/_stdio-client.ts`, and since PR #91 the typed-result round trip, which validates `structuredContent` with the client's `AjvJsonSchemaValidator` rather than zod. | It is the only public way to read the published tool list, so the gate fingerprints what a client receives instead of reaching into private SDK fields. Being a devDependency, it is absent from an installed package, so nothing on the server's runtime path may import it: `src/tools/_mcp-client-fixtures.ts`, `src/tools/_typed-result-fixtures.ts` (PR #91) and `_register-baseline.ts` are reached only from tests and the baseline writer. |
| stdout reserved for JSON-RPC | The transport owns stdout. | All logging goes to stderr ([src/logger.ts](../src/logger.ts)); `no-console` is a lint error. |

## Validation

| What | Why it is here | What it constrains |
| --- | --- | --- |
| `zod` `^4` | The only permitted boundary validator. One schema is the published shape, the runtime parse and the TypeScript type (`z.infer`). | Published descriptors are zod's own JSON Schema emission at the target the MCP SDK asks for, draft-2020-12. Until PR #89 they were `z.toJSONSchema` (draft-7) plus `normalizeToDraft7Parity`, which reproduced the retired `zod-to-json-schema` output byte-for-byte; PR #89 deleted the normaliser (068 C3). Since PR #90 every `.describe()` on an input field is published wire text (ADR-040): a wording change moves the `schemaFingerprint` and must be regenerated on purpose, and the description has to agree with the field's `docs/tools/` page. Since PR #91 the zod output schemas are published too, as `outputSchema`, and fingerprinted (`outputSchemaFingerprint`); a typed tool's handler must return `z.input` of its output schema, so a result-shape change fails `typecheck`. zod is still the only runtime validator: the SDK is handed a validator that accepts everything, for input and output alike. A zod change that alters emitted JSON Schema fails the registry fingerprint test. Since PR #101 three input schemas are a `.transform().pipe()` that folds deprecated parameter names onto new ones before the new-name schema validates; this relies on zod emitting a pipe's input JSON Schema from its published (pre-transform) side, so the old keys stay on the wire while handlers see only new names ([architecture](architecture.md#renamed-parameters-deprecated-aliases-folded-before-validation)). Lint bans the v3-era idioms (`.strict()` with no arguments, `.passthrough()`, `.strip()`) and the `zod/v3` and `zod-to-json-schema` imports (PR #78). |

## The Obsidian side

| What | Why it is here | What it constrains |
| --- | --- | --- |
| Obsidian Integrated CLI (`obsidian` binary) | The only way the server reaches a vault through Obsidian. It is not an npm dependency: it is found at runtime through `OBSIDIAN_BIN`, then the platform default path, then `PATH` ([src/binary-resolver/](../src/binary-resolver/)). | Its behaviour is the contract, and much of it is pinned only by live probes ("T0" findings recorded in `specs/*/research.md` and `contracts/`). Examples: exit 0 with `Error:` on stdout for failures, `Vault not found.` on stdout, empty stdout for `eval` against a closed vault, the cold-start `Command "<cmd>" not found.` signature. A change upstream breaks classification, not compilation. |
| A running Obsidian application | The CLI talks to it; `eval` runs inside it. | When it is closed, dispatch launches it through the `obsidian://` URI (ADR-030), unless `OBSIDIAN_AUTO_LAUNCH` is off. Everything is single-flight through one queue, because there is one app to drive. |
| Smart Connections plugin (optional) | Embeddings behind the two `smart_connections_*` tools (ADR-014, Plugin-Backed Typed Tools Runtime-Dependency Pattern). | Not installed or not yet indexed are reported as distinct errors, never as empty results. No other tool depends on it. |

## Testing and coverage

| What | Why it is here | What it constrains |
| --- | --- | --- |
| `vitest` 4 with `@vitest/coverage-v8` | The only test framework. Tests are `*.test.ts` beside their source. | `npm test` runs `vitest run --coverage`. Adding another framework needs an amendment. |
| Coverage gate: **statements only**, in `vitest.config.ts` | The single merge floor (currently 96, raised from 91.3 in PR #63). | Branch, function, line and per-file thresholds are forbidden without an amendment. Test-support files (`_*fixtures.ts`, `_registration-stub.ts`, `_schema-test-utils.ts`, JSON) are outside the denominator. |
| Structural tests | `src/cli-adapter/architecture.test.ts` (sanctioned spawn sites), `_register-baseline.test.ts` (descriptor fingerprints, read through a v2 client since PR #89), doc-presence tests on `docs/tools/`, `src/tools/_surface.test.ts` (PR #90: title, four hints, the pinned FR-024 classification and a described parameter at every depth, for every listed tool; PR #91: identical `outputSchema` in both eras with an object root, and a `structuredContent` round trip per typed tool), and `src/server.protocol.test.ts` (PR #89), which runs the same handshake and tool-call assertions for a 2025-era client over an in-memory transport and a 2026-era client through `createMcpHandler`. Since PR #143, `src/tools/_description-quality.test.ts` (spec 092 standing checks Q1–Q7: 400 characters per description, 12,000 in total, no internal identifiers in any published text or `index.md`, the `help` pointer, index entries equal to first sentences, one audit row per tool). | These fail the build for an architectural regression or an undocumented surface change, rather than relying on review to spot it. Real stdio is not exercised in CI; `npm run probe:stdio` checks it by hand against `dist/`. Neither is a real Obsidian: since PR #144, `npm run check:non-ascii` is the hand-run release check that five tools keep non-ASCII names and text exact against two real vaults, and CI runs only the unit tests of the module that decides its outcomes ([architecture](architecture.md#non-ascii-text-proven-live-npm-run-checknon-ascii)). The description checks gate only what a machine can decide; the reviewer's judgement verdicts in `_description-audit-record.json` never fail a build and show as needing review in `npm run audit:descriptions` (ADR-074). |

## Lint and format

| What | Why it is here | What it constrains |
| --- | --- | --- |
| ESLint 10, flat config, `typescript-eslint` | Zero warnings is a merge gate. | `@typescript-eslint/no-deprecated` is on and type-aware: any `@deprecated` API is an error. The low-level SDK `Server` needed explicit disables for that reason; PR #89 removed it and left no SDK `no-deprecated` disable in `src`. PR #92 brought back exactly one, in `src/tools/_confirm.ts`: on the 2025 era the only source of the client's elicitation capability is `server.server.getClientCapabilities()`, which SDK 2.4.0 deprecates in favour of a per-request envelope that 2025-era requests do not carry (research R12). It conflicts with the 068 plan's PR-3 line "no SDK `no-deprecated` disable left", and PR #92 put it to the owner (ADR-043). `import-x/order` enforces alphabetised, grouped imports. `eslint-plugin-import-x` replaced `eslint-plugin-import`, and the unused `eslint-plugin-n` went with it (PR #77). |
| `eslint-plugin-promise`, `eslint-plugin-jsonc` | Promise hygiene; JSON and JSONC linting. | `catch-or-return` and `always-return` are off, because the queue and dispatch consume promises inside `.then` by design. |
| Prettier `3.8.5` (exact hold) | Formatter of record. | Pinned exactly because of prettier/prettier#19510 (PR #75, PR #80). `format:check` is a script, **not** a CI gate, and the existing Markdown is not Prettier-clean. |

## CI

| What | Why it is here | What it constrains |
| --- | --- | --- |
| GitHub Actions, [.github/workflows/ci.yml](../.github/workflows/ci.yml) | Runs lint, typecheck, test with coverage, and build on every PR into `develop`, `release/**`, `hotfix/**` and `main`, and on every push to `develop`, `release/**`, `hotfix/**` and `main` (PR #159; before it, PRs to `main` and pushes to `main`). The push to `main` came back in PR #162. The 0.9.1 release showed that GitHub counts a push run toward a pull request's required checks but not a `workflow_dispatch` run, so the back-merge pull request #161, whose head is `main`, stayed blocked although CI had passed on its commit through a dispatched run. That pull request's own `pull_request` run was created, contrary to what PR #159 assumed, but it waited for the owner's approval because the workflow token had opened the pull request. The release cut still starts CI by `workflow_dispatch` on the branch it creates, because a branch pushed with the workflow token starts no push run; that branch's pull request into `main` gets its checks from the owner's `pull_request` run. | Matrix of **Ubuntu and Windows** × Node **22 and 24**: four jobs, `fail-fast: false`, 20-minute timeout. The Node axis came in PR #79; Windows joined in PR #87 (spec 068 A4), so path separators, junctions, `EBUSY`/`EPERM` and case-insensitive roots are exercised on every change rather than only by hand. Tests that touch the real filesystem must pass on both, which is why the containment tests build a junction on Windows and a directory symlink elsewhere. Runs in progress on the same ref are cancelled. |
| Rulesets as code, [.github/rulesets/](../.github/rulesets/) and [scripts/rulesets.ts](../scripts/rulesets.ts) | ADR-081 (Every My-Setup Code Repository Follows One Branching Model Where Main Is What npm Serves), adopted in PR #159: `main` is what npm serves, `develop` is the default branch, and only `release/*` and `hotfix/*` merge into `main`. | `protect-main`, `protect-develop` and `protect-release` require a pull request, the four CI jobs (pinned to the GitHub Actions app, so another app cannot post a check of the same name), resolved review threads, no force push and merge commits only; `main` and `develop` cannot be deleted; `protect-version-tags` stops `v*` tags being deleted or moved; nothing can be bypassed, the owner included. Approvals stay at zero for a single maintainer. Because threads must now be resolved, an open review thread blocks a merge, which the old `protect-main` (PR-only, threads not required, all three merge methods) did not. Status checks are not enforced when a branch is created, so the release cut can create `release/x.y.z` with its first commit. `scripts/rulesets.ts apply` matches the live rulesets to the files by name and also sets merge commits only, delete-branch-on-merge, Actions allowed to open pull requests, and the `npm` environment limited to `main`; `check` is the drift check, which `rulesets-drift.yml` runs daily. The drift check compares the parameters each file names, so a parameter GitHub adds later with a default is not drift, and it needs a token that can read bypass actors: the workflow token may not, and a `RULESETS_TOKEN` secret is used when present (ADR-081 leaves that token undecided). Head branches are deleted on merge, so a UAT fix goes back to `develop` through a branch cut from the release branch, not a pull request from `release/x.y.z` itself. |
| Source branch, [.github/workflows/source-branch.yml](../.github/workflows/source-branch.yml) | The required check that only `release/*` and `hotfix/*` branches of this repository merge into `main` (PR #159). | It runs on `pull_request_target`, so GitHub runs `main`'s copy of the file and a pull request cannot change the check it is judged by. It checks out nothing and reads only the event's branch and repository names. A change to the check therefore takes effect only once it is on `main`, which is why PR #159 itself went into `main` directly, before `develop` existed. |

## Packaging and publishing

| What | Why it is here | What it constrains |
| --- | --- | --- |
| npm package `@marwansaab/obsidian-cli-mcp`, `bin: obsidian-cli-mcp` | How users install and launch the server from an MCP client config. | `files` ships `dist/`, `docs/tools/**/*.md`, `README.md` and `LICENSE`. The tool docs are runtime content: `help` reads them from the installed package, and the server will not boot without them. Since PR #94, `tsconfig.build.json` also excludes the test-support modules under `src/`: the `_*fixtures.ts` files, `_schema-test-utils.ts`, `_target-mode-test-cases.ts`, `_registration-stub.ts` and `_register-baseline.ts`, joined in PR #101 by `_deprecated-params-test-cases.ts` and in PR #122 by `_note-name-locator-cases.ts`, the section editors' shared note-name rows, which import vitest. (This entry used to give a module count; it is left out because it drifts.) Only tests and scripts import them, so `dist/` holds just the files reachable from `src/index.ts`. `_register-baseline.ts` is excluded by name because it imports `_mcp-client-fixtures.ts`, and `tsconfig` `exclude` does not drop a file that a built file imports. `npm run baseline:write` runs it from source. PR #143 added `_description-audit.ts` to the by-name list for the same reason; `npm run audit:descriptions` runs it from source through the generated-vitest runner `scripts/_vitest-dump.ts`, which the baseline writer shares, because Node cannot load the `.js`-on-`.ts` imports directly. PR #144 added `_non-ascii-checks.ts`, which no built file imports, so its by-name entry only keeps it out of `dist/`. It takes the other route: it imports only `zod` and has no relative import, so `scripts/check-non-ascii.ts` loads it from source through Node's type stripping, and it must stay within erasable TypeScript syntax, which `tsc` does not check here (no `erasableSyntaxOnly`); the script's own run is the check. `npm run typecheck` still checks every excluded file through `tsconfig.json`. Before PR #94 these modules shipped in the package; PR #93's post-implement check found it. |
| Two runtime dependencies (`@modelcontextprotocol/server` and zod) | Everything else is in-tree. | A new runtime dependency must be argued in its PR against a small in-tree implementation; the bias is in-tree for anything under about 150 lines. |
| Versioning and [CHANGELOG.md](../CHANGELOG.md) | Keep a Changelog plus SemVer; the server reports `package.json` `version` in the MCP handshake. | Until PR #159, releases were cut by a version-bump commit (`chore(release): …`) on a feature PR and published from a PC, and only 0.9.0 had a tag (lightweight). Since PR #159 every PR adds its entry under `[Unreleased]`, and the version is bumped only by the release cut (see the next row). **Known gap:** the CHANGELOG has no entries between 0.6.5 and 0.9.0, so the releases in between are recorded only in commit bodies and PR descriptions. This page previously said the latest entry was 0.6.5; that was true when PR #92 was documented, but its follow-up commit `c6a2218` added the 0.9.0 entry before the merge. |
| Release cut, [.github/workflows/release-cut.yml](../.github/workflows/release-cut.yml) | The owner starts it with a version to create `release/x.y.z` from `develop`, or `hotfix/x.y.z` from `main` (PR #159). | Only the repository owner may run it; anyone else's run fails with a message. The new branch is created already holding its one commit: `npm version` sets `package.json` and `package-lock.json`, and `scripts/release.ts cut` renames `[Unreleased]` to `[x.y.z] - YYYY-MM-DD` (UTC date) under a fresh empty `[Unreleased]` and moves the link references. Nothing is pushed to an existing protected branch. It refuses a branch that already exists. |
| Version and changelog, [.github/workflows/release-checks.yml](../.github/workflows/release-checks.yml) | The required check on PRs into `main` (PR #159). | `scripts/release.ts check` fails unless `package.json`'s version is greater than npm's `latest`, read from the registry's dist-tags, and `CHANGELOG.md` has a non-empty dated section for it. Versions must be plain `x.y.z`; there is no prerelease channel (ADR-081 leaves one undecided). It runs from the pull request's own code, unlike Source branch. It failed on PR #159 itself, as expected: that PR kept 0.9.0. |
| Release, [.github/workflows/release.yml](../.github/workflows/release.yml) | Publishes each merge into `main` to npm (PR #159). | Three jobs. `plan` reads the version and stops if `vX.Y.Z` is already tagged, which is how PR #159's own merge published nothing. `publish` runs in the GitHub environment `npm` (deployments from `main` only), tests and builds on Node 24 with npm 11 (trusted publishing needs npm 11.5.1 or later), and runs `npm publish --provenance` through npm trusted publishing: no npm token exists in the repository or on a PC, and npm's trusted-publisher entry names this file and the environment. Provenance needs `package.json` `repository` to name this repository, which PR #159 added. `release` runs only after a successful publication: it creates the annotated tag on the published commit, the GitHub Release from the version's changelog section, and the pull request `main` into `develop` (reusing one already open), whose required checks come from CI's push run on the same `main` commit (PR #162; PR #159 started a CI run by hand instead, which GitHub did not count). Each of its steps skips what an earlier attempt did, so *Re-run failed jobs* finishes a part-way failure (PR #159 review). A failed publication leaves no tag and no Release. |
